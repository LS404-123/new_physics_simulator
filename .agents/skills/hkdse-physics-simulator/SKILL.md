# HKDSE Physics Simulator

把香港中學文憑物理的概念、實驗過程和數據處理轉化為可操作、可觀察、可驗證的互動模擬器。模擬器可用來建立概念、診斷誤解、練習儀器操作、量度、記錄、數據處理、分析或實驗評估；核心是讓學生完成能顯示學習成果的物理任務，而不是把公式或實驗步驟搬到網頁。

## 工作流程

### 1. 先分清來源與要求

- 若使用者提供圖片、教材、批註或文件，先分開「來源內容」、「文件內的指示／問題」和「使用者真正要求」；不要把文件中的問題誤當成實作規格。
- 確認 HKDSE 課題、學生對象、要呈現的物理量、單位、假設和邊界。
- 只使用來源已支持的物理內容。若題目、條件或預期互動有多個合理解讀，先提出具體澄清問題。

### 2. 先確定用途與學習證據

先選擇一個或多個實際需要的用途：

- **概念建立／因果關係**：觀察變量如何互相影響並作物理解釋。
- **誤解診斷／修正**：先作預測，再用可見證據檢驗想法。
- **實驗操作／量度**：選擇及設置儀器、控制變量、讀數和記錄。
- **數據處理／分析**：整理表格、重複讀數、計算衍生量、繪圖、求斜率或截距並作結論。
- **探究／評估**：設計公平測試、辨認誤差來源、判斷數據質素和提出具體改良。

在寫程式前，明確寫出：

1. 學生完成後應做到或說出甚麼；
2. 哪一項可觀察的操作、記錄、計算、圖像或解釋能證明他已做到；
3. 需要由學生練習、不能由介面代辦的關鍵步驟；
4. 只有在相關時，才列出要診斷的誤解、常見程序錯誤或數據處理錯誤。

優先呈現與目標直接相關的物理證據。概念活動先讓學生看見關係；實驗活動保留需要練習的操作；數據活動讓學生處理原始數據後才顯示檢查或示範答案。

### 3. 把學習目標拆成可觀察的流程

預設採用以下共通三段式，按教學用途改變每段的任務，毋須強行套用同一種互動：

1. **定向／預測／計劃**：展示目標、初始狀態和已知條件；要求學生作預測、選擇裝置或計劃量度（只採用與目標相關的項目）。
2. **操作／量度／記錄**：學生改變有物理意義的條件、操作儀器並取得觀察或原始數據；概念活動則觀察動畫、圖像、讀數或向量如何回應。
3. **處理／解釋／驗證**：學生處理數據、繪圖、比較、作結論或解釋物理關係，再獲得針對其操作和推理的回饋。

例如，概念活動可用「預測 → 操控 → 解釋」，實驗活動可用「設置 → 量度及記錄 → 分析及評估」。每一階段都要有「學生操作」、「畫面可見變化或數據產物」、「提示問題」和「完成條件」。只在探索或評核需要時隱藏答案；不要以揭示答案取代有意義的回饋。

### 4. 設計物理模型與實驗數據

- 將真實物理狀態、儀器反應、學生記錄的原始數據、處理後數值和結論分開儲存及按需要顯示。
- 所有顯示的數字都要有單位和清楚標籤；若是原始讀數、刻度位置或示意量，明確標明不是實際物理量。
- 圖表的 x、y 軸範圍要固定或有清楚理由地更新，避免學生把自動縮放誤解為物理變化。
- 實驗活動要清楚區分自變量、因變量和控制變量；儀器量程、最小分度、讀數精度和有效數字須互相一致。
- 數據表把物理量與單位放在欄目標題；重複讀數、平均值、衍生量、圖像、斜率、截距和不確定度只在學習目標或來源要求時加入。
- 不要自動完成學生應練習的數據處理。可提供逐步檢查、容許修正，並把學生結果與示範結果分開顯示。
- 不要為了「像真」而隨機加入雜訊。只有在隨機誤差、數據散佈或評估數據質素屬學習目標時才模擬非理想數據，並保持物理上合理及可重現。
- 只暴露有助理解的參數；不為未提出的需求加入可配置系統、資料庫或框架。
- 對碰撞、力、運動、能量、熱學、電學等不同課題，選擇最能讓學生看見因果關係的表示法：動畫、向量、時間圖、能量條或讀數對照。

### 5. 設計 iPad Air 介面

- 以單一 iPad Air viewport 完成整個學習流程為硬性要求：頁面不可出現垂直或水平捲動。若內容超出 viewport，重新分配資訊、縮短說明或折疊次要內容，不要用捲動掩蓋版面問題。
- 以單頁、橫向優先的工作區設計，並支援直向排列；若專案已有約 (1100\times700) 的模擬尺寸規範，沿用該上限。沒有指定最小 viewport 時，至少以保守的 1024×768 CSS viewport 檢查。
- 使用 `100svh`、`min-height: 0`、safe-area padding 和可收縮的 grid／flex 區域；只有在確認全部內容都能放入時才使用 `overflow: hidden`，不能用它剪掉學生需要的控制或結果。
- 把 viewport 內的資訊按優先級固定排列：課題／階段、主要模擬場景、下一個操作、關鍵讀數。長篇背景、公式和延伸解釋放在可展開區域，不可佔用主要操作的空間。
- 使用 `viewport-fit=cover`、safe-area padding、至少 44–48 px 的觸控目標和可見 focus 狀態。
- 不依賴 hover、右鍵或極細刻度；拖曳要有吸附、放大可見的目標，並支援手指及 Apple Pencil。
- 版面通常分為：大型模擬區、控制／提示區、重要讀數區。重要結果不能只藏在 tooltip 或彈窗。
- 讓操作按鈕說明「會發生甚麼」，例如「放入冰水」、「記錄讀數」、「檢查圖線」，不要使用空泛的「提交」或「下一步」。
- 可使用 Bento 或輕量 Glassmorphism，但不能降低刻度、圖表、向量、標籤和關鍵讀數的對比度。
- 尊重 `prefers-reduced-motion`，動畫要服務於觀察熱平衡、運動改變或讀數穩定，而不是裝飾。

### 6. 實作方式

- 先檢查目前專案的資料夾、既有頁面、樣式和 helper，再決定要新增或修改哪一個檔案。
- 若沒有框架要求，使用單一 HTML 檔案內的 CSS 和原生 JavaScript；不要為簡單模擬加入新依賴。
- 保持 HTML、CSS、JavaScript 結構清楚；把物理常數、狀態、畫面更新和事件處理分開，但不要建立只有一個用途的抽象層。
- 對公式使用 MathJax 只在公式是學習目標且專案已有或確實需要時；若數學只是補充，優先用簡單文字或隱藏的補充區。
- 先完成可操作的最小雛形，再檢查數字重疊、標籤遮擋、狀態轉換和重要資料提示，最後才調整視覺樣式。

### 7. 驗證與交付

- 至少執行 HTML／JavaScript 語法檢查，以及一個會在物理狀態或數據處理邏輯出錯時失敗的最小 runnable check。
- 手動逐步測試：初始狀態、每個控制、等待穩定、錯誤操作、完成條件、重設和重新開始。
- 按教學目標確認需要學生完成的操作不能被跳過；檢查原始數據、處理結果、單位、精度、圖軸、回饋和示範答案一致。
- 在最小目標 viewport 的橫向及直向模式檢查 `scrollWidth <= clientWidth` 和 `scrollHeight <= clientHeight`；若不成立，先改版面，不要只加捲動。
- 使用 `browser:control-in-app-browser` 做本地頁面視覺及互動檢查。若該瀏覽器不可用，直接報告限制，不要改用其他瀏覽器自動化。
- 交付時列出新增／修改檔案、完成的互動、已執行的檢查、採用的物理假設和未處理的範圍。
